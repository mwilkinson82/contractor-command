# AP reconciliation snapshot — staged contract v1

`public.mcp_cost_reconciliation_snapshot(job_uuid)` is a read-only proposal in `ap-reconciliation-snapshot.schema-draft.sql`; it is not an applied migration. The caller must be active, a current owner or AP member of the resolved company, and have full scope on the requested job. In one SQL statement, the function selects relevant cost records and all versions, checks company and full access to every affected job in every version, and constructs the response from that same database snapshot. Any inaccessible, inconsistent, over-limit, or unauthorized result is the same generic object:

```json
{"snapshot_version":1,"complete":false,"status":"unavailable"}
```

No record IDs, financial rows, or count of hidden records accompany an unavailable response. The entitlement check is read-only and fails closed for inactive or uncertain entitlement. It reads the canonical Circle decision and an active purchased plan or active company-owner entitlement, rather than calling the usual gate that can provision accounts or accept invitations. This narrower check can leave otherwise eligible users unavailable until membership and entitlement data are synchronized. An absent RPC, unknown `snapshot_version`, malformed response, error, or unavailable result must remain unavailable to reconciliation; it must not fall back to the partial cost reader.

A complete response includes `snapshot_version: 1`, `complete: true`, `status: "complete"`, `company_id`, `job_id`, and `ap` containing:

- `coverage: "athena_cost_records_only"` and `external_accounting_coverage: false`: completeness covers records in this cost subsystem, not an external accounting system or the whole company ledger.
- `cents_encoding: "decimal_string"`; each total, job allocation and settlement amount is a positive integer string up to `9000000000000`. There is no single company-wide currency: top-level `currency` stays null and `currency_verified` stays false. `currency_coverage: "per_version"` means each version exposes its supplied `currency_code` and `currency_source`; missing legacy currency stays null/unknown. A review confirmation is not independent proof of the source document. Only the pinned two-decimal codes are supported; do not combine different or unknown currencies.
- `records[]`: `id`, `kind`, `posted_version`, all `versions[]` with `version`, `recorded_by`, `recorded_at`, `reason`, `incurred_on`, `currency_code`, `currency_source`, `amount_cents`, `document_reference`, `counterparty_name`, and `allocations[]` (`job_id`, `cost_code`, `amount_cents`); accounting approvals with version, actor and `approved_at`; posting events with version, actor, `posted_at`, and nullable `accounting_effective_on`; PM/owner business approvals with version, job, amount, basis, notes, actor, time and any withdrawal; single-record `payments[]` with ID, amount, date, reference, recorded time and correction lineage; and `shared_allocations[]` with this record's allocation, payment ID, date, reference and correction lineage.
- `accounting_effective_date_coverage: "per_posting"`; `accounting_effective_date_available` is true only if posting events exist and all included posting dates are known. Each posting has its own explicitly reviewed `accounting_effective_on`; older absent values stay null. `settlement_allocation_by_job_available: false`, `original_evidence_coverage: false`, and `shared_payment_conservation_available: false`. The shared header total and other records' allocations are not supplied. Do not infer a job payment share, missing accounting effective date, receipt presence, shared-payment conservation, bank transfer or refund. Company-paid expenses are costs, not supplier payables or reimbursements. A later unposted correction does not replace the latest posted version.

The maximum is 200 relevant records and 1,000 rows in each included version, approval, posting, payment, shared-allocation and correction set, with a final serialized AP object no larger than 2 MiB. Oversize produces only the generic unavailable object. Individual versions are capped at 100 allocation lines and 30,000 bytes; malformed amounts, inconsistent company/job references and incomplete permission scope also fail closed. This contract assumes the staged writer and direct-table revocations are intact; preflight must verify schema integrity and investigate any privileged out-of-band writes before treating it as complete.

Synthetic PGlite tests cover role and company denial, hidden split scope, changed membership, version correction, approvals, settlement correction lineage, maximum cents, over-limit values and output/row bounds. A separate temporary PostgreSQL 18.4 lab runs snapshots in read-only transactions and exercises eight concurrent version/approval/posting commits and concurrent access revocation using independent connections. These checks do not authorize production or establish managed-database performance. Review indexes, role gates and Supabase advisors, integrate the ordered migration, and validate the consumer against the exact reviewed schema before enabling AP findings.
