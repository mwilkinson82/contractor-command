# Direct drawing upload and source-bound markup

The drawing card can send a selected local PDF through the host's existing authenticated tools/call bridge to drawing_set_import. PDF bytes do not pass through model-generated text; no public staging URL, new endpoint, credential, bucket, table, migration or permission is introduced. The existing backend validates PDF bytes/pages, the 50 MB drawing limit, membership/job scope and duplicate hashes. Original drawings remain immutable; generated markup stays within athena-files' existing 10 MB cap.

A no-file import request returns the upload card for the resolved job. Failed imports return stored:false and an upload retry context. If the original/source record was saved but the legacy takeoff-index sync fails, the result truthfully reports stored:true,index_synced:false; retry recognizes the same original. No automatic upload occurs. The member chooses a PDF and clicks Store PDF on this job. The control remains disabled unless the host advertises serverTools; whether live Claude grants it requires acceptance testing. Hosts' payload/time limits still apply and are not bypassed.

Markup save requires a source_id or source_filename; an unbound save becomes a named-source preview with saved:false. A requested source not present on this job never falls back to an older set. Every card identifies filename, source date/revision and fingerprint and says a failed new upload is not included. Athena cannot infer bytes the host never supplied. A source ID is preferable to a filename when selecting a specific historical revision. Reindexing a stored file performs one binary download and fingerprint/page checks in its recorded bucket; it does not turn the entire original into base64 and import it again. This removes the large string-allocation path observed during the live 17.6 MB reindex failure, whose server root cause is not yet confirmed by logs.

Prepare returns the actual original PNG plus factual drawing_annotations. Supplied normalized coordinates show numbered blue pins on that original preview; real risk/delay pins are red. Unlocated findings receive no invented coordinates. The member can select a finding, tap its location on the actual sheet, then save the located annotations against the exact source ID. Nothing is saved by placing a pin alone. The existing server renderer produces the dated PDF and raster preview; originals and quantities are unchanged. The card also reports the number of pins on the sheet, so an unlocated key is not presented as plotted findings. Model-supplied lines/areas still draw in the saved PDF; the positioning control places pins.

Drawing resource v3 forces a fresh view; v2 and the original resource stay readable. Existing ChatGPT widget/outputTemplate, contract/SOV/morning/email cards are unchanged. No email, auth, Hub or migration changes.

Private QA: a real browser file chooser delivered an entire 2,900,000-byte fictional PDF to the local mock host; a tap on the actual local S-100 image produced a blue numbered pin and an exact-source save request. No production upload/save was made by those interaction fixtures. Phone preview at390px has no page overflow. These local results are not a live Claude/ChatGPT/Grok Bot upload or save pass. Live tests must verify host bridge capabilities, tool calls, persisted source/markup version, original hash, pins and private PDF opening after an approved Lovable publication. Takeoff quantity accuracy remains unscored.
