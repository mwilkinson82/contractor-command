# Job cost foundation — staged submission vertical slice

This is **not a released Athena feature**. The local slice contains registered-in-draft conversational review/save/read tools and SQL staged as a schema draft, tested together using synthetic PGlite fixtures. The SQL is not in the migration directory and has not been applied to a live database. It persists and exercises submission, approval, posting and settlement in the test database only. The staged accounting authority hook denies every caller; it cannot authorize those actions in production. It does not store original files or transfer funds. Do not register or deploy it before coordination and review.

## Audited existing contracts

At base `bda3539b`, `billing_evidence_record` handles customer invoices, credits, receipts and allocations; it is not a supplier payable or job-cost ledger. Budget cost codes are supplied strings in `mcp_job_facts`, not an established company-wide registry. The latest staged team/access migrations replace the old `finance` role with `ap`: allowed roles are `owner`, `all_access`, `ap`, `pm`, `estimating`, `contracts`, and `super`. The current job scope grants `full` to owner/all_access/ap and assigned PM, subject to the role/plan gate; that scope alone does not establish accounting authority.

Proposed policy for decision: full-scope members may submit/read; `owner` and `ap`, each with full scope to all affected jobs, may approve, post and record settlement. Under existing scope, owner, all_access, AP and an assigned PM may submit and read; estimating, contracts and super are excluded. This does not add a field-superintendent submission route. Do **not** assume `all_access` or `pm` have accounting approval, posting or settlement powers without an explicit policy decision. This is a proposal only: staged approval, posting, recording settlement and correcting settlement evidence call an authority hook that always returns false, and no existing role or privilege is changed. The proposal permits the same authorized actor to submit, approve and post; separation of duties is not currently required. Production authority policy remains unresolved.

Draft PR #352 at head `5ebe3888d2869405b0ce9a4d0e4b069eec72e357` proposes project-linked `mcp_project_parties(id, job_id, company_id, name, kind)` and `mcp_purchase_orders(id, job_id, company_id, party_id, number)` plus append-only PO versions. These are not merged at this base. The staged SQL rejects links if the corresponding tables are absent and validates company, job and matching party when synthetic contract tables exist; linked entries may allocate only to the linked job. The chat schema does not expose these provisional references yet. The eventual integration must enforce referential integrity and coordinate deletion/updates and PO revision snapshots; the staged lookup alone cannot guarantee those properties. PO value is a commitment, never a posted expense or payment.

## Staged contracts

The draft registers `job_cost_submission_record` and `job_cost_submissions_read` identify the company and job, gather sparse facts, display the exact allocations and missing original, then save only after explicit confirmation using the reviewed payload and request ID. A lost response is reported as unknown; the client must read and retry the same request, not issue a new ID. They only submit cost metadata, never claim accounting posting or payment. An original is always `missing`; a document reference is metadata, not proof that bytes were saved. Ad hoc field expenses need no PO or subcontract. Split allocations must conserve integer cents and all referenced jobs must belong to the company and be accessible at full scope.

The SQL (`job-cost-submission.schema-draft.sql`) provides append-only submission versions, company-serialized writes, duplicate document-reference tracking, optimistic corrections, idempotent operations, active-member gating and full access to the anchor and every historical and proposed allocation. Direct table access is revoked. A reader excludes a split record unless the caller can access all its historical jobs. Staged approval, posting and settlement functions are guarded by a fail-closed accounting-authority hook. The registered-in-draft accounting tool shows a review and requires confirmation; it cannot proceed while the hook denies access. A test-only override exercises transitions and is never included in the staged SQL. The draft tools and staged SQL are not a substitute for a security review or an operational migration. The review key is an unkeyed hash in the client tool; direct authenticated RPC callers can bypass the conversational confirmation. Database approval-before-post is enforced, but the user-confirmation boundary requires a server-side review-ticket design and tests before release.

Duplicate detection is conservative: same kind, normalized counterparty name and reference within a company, including historical versions. Aliases and missing references can evade detection, while different same-name parties can collide. The supplier track must supply stable identity and a reconciliation plan. Posting events refer to approved immutable versions; a correction keeps the earlier posted version in effect until its approved successor is posted. Payment evidence is separate from cost and capped at the posted payable; company-paid expenses have no reimbursement payable. Pending corrections block new settlement, and a correction cannot be posted below recorded settlement or with a changed payee. Staged shared settlement requires fully allocating a single payment across posted payables, conserves cents, checks every affected project, rejects duplicate references and requires the same recorded payee. It remains fail-closed until the provisional supplier/payee identity contract is validated; matching names alone do not establish identity. A whole-entry evidence correction requires a reason, preserves history and restores the recorded payable; it never means a bank reversal or refund. Partial corrections, actual refunds and a conversational shared-payment/correction workflow are not implemented. Production posting authority, tax, P&L and W-9 remain unimplemented.
