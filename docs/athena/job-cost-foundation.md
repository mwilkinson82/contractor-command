# Job cost foundation — staged submission vertical slice

This is **not a released Athena feature**. The local slice contains unregistered conversational review/save/read tools and SQL staged as a schema draft, tested together using synthetic PGlite fixtures. The SQL is not in the migration directory and has not been applied to a live database. It can persist submitted cost metadata in the test database; it cannot approve, post, record settlement, store original files, or transfer funds. Do not register or deploy it before coordination and review.

## Audited existing contracts

At base `bda3539b`, `billing_evidence_record` handles customer invoices, credits, receipts and allocations; it is not a supplier payable or job-cost ledger. Budget cost codes are supplied strings in `mcp_job_facts`, not an established company-wide registry. The latest staged team/access migrations replace the old `finance` role with `ap`: allowed roles are `owner`, `all_access`, `ap`, `pm`, `estimating`, `contracts`, and `super`. The current job scope grants `full` to owner/all_access/ap and assigned PM, subject to the role/plan gate; that scope alone does not establish accounting authority.

Proposed policy for decision: full-scope members may submit/read; `owner` and `ap`, each with full scope to all affected jobs, may approve, post and record settlement. Do **not** assume `all_access` or `pm` have these accounting powers without an explicit policy decision. This is a proposal only: the SQL adds no approve, post, or settlement function, and changes no existing role or privilege. Production authority policy remains unresolved.

The PO track proposes project-linked `mcp_project_parties(id, job_id, company_id, name, kind)` and `mcp_purchase_orders(id, job_id, company_id, party_id, number)` plus append-only PO versions. These are not merged at this base. The staged cost SQL rejects party/PO IDs rather than treating unvalidated references as valid. After integration, validate each ID against the exact job/company and require the PO's party to match when both are supplied. PO value is a commitment, never a posted expense or payment.

## Staged contracts

The unregistered tools `job_cost_submission_record` and `job_cost_submissions_read` identify the company and job, gather sparse facts, display the exact allocations and missing original, then save only after explicit confirmation using the reviewed payload and request ID. A lost response is reported as unknown; the client must read and retry the same request, not issue a new ID. They only submit cost metadata, never claim accounting posting or payment. An original is always `missing`; a document reference is metadata, not proof that bytes were saved. Ad hoc field expenses need no PO or subcontract. Split allocations must conserve integer cents and all referenced jobs must belong to the company and be accessible at full scope.

The SQL (`job-cost-submission.schema-draft.sql`) provides append-only submission versions, company-serialized writes, duplicate document-reference tracking, optimistic corrections, idempotent operations, active-member gating and full access to the anchor and every historical and proposed allocation. Direct table access is revoked. A reader excludes a split record unless the caller can access all its historical jobs. The unregistered tools and staged SQL are not a substitute for a security review or an operational migration.

Duplicate detection is conservative: same kind, normalized counterparty name and reference within a company, including historical versions. Aliases and missing references can evade detection, while different same-name parties can collide. The supplier track must supply stable identity and a reconciliation plan. The separate pure domain model explores approval, posted-version replacement and settlement without adding another cost; those operations are **not implemented in the SQL or conversational path**. Payment reversals, payment allocations across bills, reconciliation after payment, posting authority, tax, P&L and W-9 remain unimplemented.
