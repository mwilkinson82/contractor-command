# Job cost foundation — draft integration boundary

This is an unconnected domain prototype, not a usable Athena feature. It does not persist records, register chat tools, accept file bytes, perform an accounting integration, or enforce server-side authorization. Do not merge or release it as a completed job-cost workflow. No customer data or live database was used.

## Audit of the accepted base

At bda3539b, `billing_evidence_record` handles customer invoices, credits, receipts and allocations through `mcp_billing_evidence_record`; it is not a supplier payable or job-cost ledger. The MCP server resolves the job at `full` scope and the billing database functions call the active-membership gate and check `mcp_job_scope`. A budget uses supplied cost-code strings in `mcp_job_facts`; the audited code does not establish a company-wide cost-code registry. No supplier or PO database contract from the parallel track is assumed here. The model accepts a human counterparty name and optional opaque counterparty/PO references, but **does not validate those references**. An original can only be marked `missing`; a document reference is metadata, not proof of a stored original.

## Domain contract

`applyCostCommand` takes a ledger snapshot, company/actor and full-job access predicate, request ID, and one submit, correct, approve, post or payment command. Every allocation has a job, supplied cost code and positive integer cents; allocations must exactly sum to the entry amount. All jobs in all versions of a record require full access, including when reading one side of a split. An approval is a recorded status transition; it does not establish that the actor has accounting authority. A correction produces a new submitted version; the last posted version remains effective until the correction is approved and posted. Payment evidence is distinct from a cost and cannot exceed the posted payable or reimbursement. Company-paid expenses create no reimbursement payable. No transfer is made. Supplier bills, company-paid expenses, and reimbursable expenses are separate kinds; a PO is optional for supplier bills and is not a cost.

The duplicate check flags matching kind, normalized counterparty name and document reference within the company, including historical versions. This is deliberately conservative and is not a reliable identity resolver: aliases and missing document references can evade it, and two same-name counterparties can collide. The supplier track must provide stable company-scoped identity and a migration/reconciliation strategy. Settlement references are unique only within a cost record; a real shared payment allocated across several bills needs a separate payment/allocation design. Payment reversal/correction and voiding are not implemented. A paid record cannot be reposted below its paid amount or assigned to a different payee until settlement is resolved. `postedCosts` returns cost allocations only, never settlement. It does not calculate a P&L, tax or W-9.
