# Job cost release preflight and synthetic acceptance — review draft

Do not apply, merge, or deploy from this plan. The coordinator must first choose the ordered release and migration identities after checking managed migration history. The cost and receipt SQL files in this branch are drafts, not migrations. Generate the final migration through the supported Supabase CLI once the final PO and financial-original migrations and review are settled.

## Dependencies and preflight

1. Verify the exact release and draft heads, their final required CI results, managed migration history, and a tested backup/restore point. Confirm there is no migration timestamp collision. Verify migration changes preserve existing nullable posting dates and version facts without backfilling guessed currency or dates. Verify the PO tables and immutable `(po_id, version)` revisions match the reviewed contract; validate company, job, party and snapshot against that contract. Confirm the financial-document bucket exists, is private, and has no authenticated object policy granting direct access. Verify server-side storage credentials remain server-only.
2. Review both schema drafts as one coordinated transaction with their prerequisites: active membership and job scope functions; company and job tables; financial-original storage; the PO schema; and the owner-approved role mapping. Run Supabase security and performance advisors in a disposable environment, inspect exposed SECURITY DEFINER functions and grants, validate indexes, and confirm no PUBLIC or anonymous execution. Test the server-issued review ticket and the host confirmation UX; a boolean is not independent proof that a person approved an action.
3. Deploy schema and application together under the release coordinator's plan. Keep the shared-payee identity gate false. Do not enable shared payment recording or infer a common payee from names. Ensure the receipt upload route and receipt schema are deployed together, as the route consults the new upload table for otherwise unknown links. Review orphan-object retention and cleanup before enabling uploads; never delete originals during rollback.

## Isolated synthetic acceptance after coordinated deployment

Use an explicitly provisioned isolated test tenant, synthetic files and identities only, after the coordinator authorizes the deployment. Verify jobs, company roles and membership before running. Never use an actual customer's bills, files or bank data.

- Submit a field expense as an assigned superintendent, store a small synthetic receipt, finish it twice with the same upload ID, list and read that exact receipt, and confirm its size/hash. Verify another superintendent, unassigned user, wrong record, wrong job, wrong company, revoked member, direct table access, and direct bucket access cannot read or upload it. Test an expired link, exhausted attempts and mismatched bytes. Confirm the same user cannot read the ledger or accounting statuses through the receipt flow.
- As owner/AP, read the linked synthetic receipt; confirm supplier invoices and other unrelated originals cannot be accessed through the receipt ID. Verify the original missing at submission is not represented as an attachment until receipt registration succeeds. Review the retained-original audit and orphan handling.
- Create a synthetic supplier bill with the exact project party and PO revision; reject missing, foreign, mismatched, changed-snapshot and nonexistent revision references. Verify ad hoc field purchases work without a PO. A PO changes no posted costs and does not imply payment.
- Test each affected job's PM approval, withdrawal, correction and reapproval. Record accounting approval, posting and synthetic settlement evidence as owner/AP; confirm no transfer occurs and no settlement adds expense. Race duplicate references, exact retries, overpayment and withdrawal against recording using independent connections.
- For reports, reconcile latest posted version against posting events and its per-job allocation. Treat `posted_at` as Athena's recorded posting timestamp and `accounting_effective_on` as the separately reviewed owner/AP-supplied accounting date. Confirm that a missing historical date or currency stays unknown, and do not combine different currencies. Corrected versions expose their own `recorded_at`; only a posting event makes one effective in this model. Settlement is recorded at the whole-record level; no job settlement allocation is available and reports must say so.
- Verify the final release manifest and all required checks on the exact deployed head. Confirm review and deployment telemetry contains no receipt bytes or credentials.

## Containment and rollback

If any preflight or acceptance check fails, stop release and disable the new cost and receipt tools at the coordinated application boundary. Preserve immutable versions, approvals, posting and payment evidence, receipt metadata, and stored files. Revoke only new feature RPC execution through a reviewed emergency change if containment requires it; do not broaden any other role. Restore the prior compatible application if safe, record exactly which schema and writes exist, and use a reviewed forward fix or tested backup restoration plan. Do not drop tables or objects or delete user originals as an automatic rollback; reversing recorded evidence is not a bank refund. Resume only after scoped re-verification and coordinator approval.
