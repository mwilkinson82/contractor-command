# Project parties and purchase-order drafts

Athena's purchase-order path resolves a full-access project and a project-linked party. A member can record a party's identity, trade, contact information and textual insurance/contract references, then create and retrieve purchase-order drafts. A party update retains its previous snapshot. A purchase order records line descriptions, quantities, units, unit prices in USD cents, order and needed-by dates, and the exact terms version. Draft and reviewed revisions are commitments only; no entry posts a cost or payment.

Company owners explicitly record approved company terms and separately select the default using an expected company-default version. Each successful selection appends an immutable event. Stale selections fail and must be reviewed again. Only owners can see the company-wide terms catalog and default history. Other full-access project members can see company terms only after an owner has attached that version to a PO on their job; supplier and PO variants remain visible only within their own job. Supplier-specific or PO-specific variants retain the exact text, source, change note and parent version, and do not alter the company default. The chat tool returns the base and revised text and a bounded line comparison; the project page shows both texts. This is not a document redline editor or a file-attachment store, and recording a variant does not prove supplier acceptance. A PO-specific variant applies only to its named PO. Later attachment work must preserve actual redline files separately.

Athena asks for missing facts, shows company, job, party, line prices and terms, and sends an explicit confirmation signal before saving. A server-side, expiring review binds a SHA-256 payload digest to actor, job, action and request; it stores no terms or contact content. The confirmation flag signals the client’s assertion, not independent proof that a human approved. Expired review hashes are cleaned opportunistically; a previously applied request can be retried with its original review ID after expiry. A request ID is tied to the actor, action, reviewed payload and review ID for retries; an unknown outcome requires reading the records and retrying the same request. The database checks active membership and full project scope, serializes writes by job, validates references and versions, and retains immutable PO, party and terms history. Issued and accepted versions are recognized for future integrations but cannot be created or revised by this slice; nothing is issued, sent, signed or accepted here. The signed-in project-home page is read-only and uses the same database gate.

## Interface and release coordination

The provisional cost interface links an exact PO revision with the composite key `(po_id, version)` in `mcp_purchase_order_versions`; the cost workflow must distinguish PM payment approval from actual payment by accounting or an owner. The provisional counterparty key is `mcp_project_parties.id`, with `company_id` and `job_id`; this is a project record, not a shared company-wide vendor master. `mcp_purchase_orders.id` has `company_id`, `job_id` and `party_id`; `mcp_purchase_order_versions` is keyed by `(po_id, version)` and snapshots the party. Any future cost-entry reference must check exact company and job ownership and ensure a selected PO's party matches the selected party. Do not infer actual costs, invoices or payments from a PO.
