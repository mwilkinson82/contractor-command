# Recorded supplier-payment correction — local release candidate

This change connects a contractor's request to correct a recorded payment through read, review, explicit confirmation, atomic save and durable readback. It records accounting evidence; it does not transfer, refund or reverse money, approve work, or change a posted cost.

## Source and scope

- Original Lovable project: `362c776b-68ab-4871-bedb-c42cb9843c1b`; read-only checks at start and finish report `5aad97fed9efaa745ddbe349bf1f0adf0fba10bd`.
- Prepared in an isolated repository and worktree; controller files were read only. Local baseline `288be10` reconciles the controller's verified source and managed support migration 0043. The current live job-cost tool was independently fetched and matches that baseline byte for byte. Verification artifacts remain in the private controller handoff.
- Existing SQL was inspected in source and through read-only function-definition queries. Its correction action only excluded an erroneous payment from the active balance; it did not atomically replace facts or bind current payable state.
- No existing customer payment was changed, and no prior unsaved attempt was saved or reused. Customer record identifiers and references are excluded from this release documentation. No remote writes, browser/CUA, credentials, messages, roles, entitlements, pushes or publication occurred during implementation.

## Customer path and invariants

1. `job_cost_submissions_read` identifies the exact existing cost record and recorded payment. `job_cost_payment_correction`, step `read`, returns that identity, current payable versions, source facts, correction history and an opaque current-state token.
2. Step `review` requires that token, a reason and either complete revised facts/all original payable allocations (`replace`) or explicit removal of erroneous evidence (`void`). It shows prior/revised amount, date and reference, affected bills and versions, and whole-payable paid/unpaid effects. Nothing financial is saved at review.
3. Only after explicit confirmation does step `save` receive the exact server-produced payload and actor/job-bound review key. The review expires after 15 minutes. A company-row lock serializes this action with the existing cost/accounting/settlement writers. Changed cost facts, versions, approval history, payment history or balances require another read and review.
4. One transaction appends the correction, optional replacement evidence and operation audit. Original identity/facts remain immutable. The replacement ID is disclosed in the reviewed payload and linked in the saved operation; it is never an unrelated new-payment fallback. The old create-payment review rejects a supplied existing payment ID. New calls through the legacy void-only correction path must use this reviewed flow; completed legacy request retries still return their existing result.
5. Repeated confirmed saves return the same result under the same request ID. Changed content/actor under that ID is rejected. An uncertain transport outcome retains the exact payload/key; inspect history and retry that request without a new review or payment ID.

Owners/AP retain the existing accounting gate and full-company scope. PM business approval remains separate from accounting approval/posting. Replacement requires a current posted payable, supported consistent currency, current PM coverage and no overpayment or conflicting active reference. Removing erroneous evidence can restore a payable after approval withdrawal without creating an approval or refund. Shared corrections preserve the original payable identities and conserve header/allocated cents; they do not enable new shared-payment creation or a general ledger editor.

The SQL proposal adds three functions and append-only triggers, reuses existing review tickets/correction/operation tables, and closes the legacy correction write path. It adds no tables, columns, roles or entitlement policy. `payment-correction-proposal.sql` is deliberately unregistered and has never been run remotely. The release controller must generate a managed migration after 0043, verify the expected legacy function source and preserve its ACL.

## Balance and reporting meaning

Review/save effects are **whole-payable** balances, including partial payments. A cost split across jobs is not silently divided into proportional settlement. The existing reconciliation snapshot sees the original as corrected and the replacement as active; posted versions and costs remain unchanged.

Optional `as_of` on correction reads reports whole-payable evidence known by the end of that UTC day. It requires both `paid_on` and immutable recording time to precede the cutoff; a correction takes effect in this view after its immutable correction time. Posted versions also require known recording and explicit accounting-effective dates. Unsupported/mixed historical currency or missing effective dates return Unknown. This is a known-at evidence view, not an invented accounting-effective correction date or bank balance. The broader accounting report continues to withhold unsupported per-job AP settlement totals; this change does not claim that separate reporting gap is complete.
