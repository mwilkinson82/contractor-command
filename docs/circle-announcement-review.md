# Review Circle announcement recipients

The Hub admin preview separates verified recipients, unresolved membership holds and marketing suppressions. A hold never becomes eligible because it was acknowledged. The existing ANNOUNCEMENTS template, sender, reply-to, LovableEmail provider and transactional queue stay in use.

For Circle, Circle without a sign-in, and Control baseline campaigns, refresh the audience and inspect its recipient and exclusion lists. Acknowledge that exact list and type `SEND`. On submission the server rebuilds the audience and verifies its deterministic hash and exact held-email set before creating an announcement or queue entry. A changed recipient, identity binding, hold reason, campaign filter result or suppression requires a fresh review. Calls without a review object retain fail-closed behavior when holds exist.

Canonical membership and native marketing suppression are separate decisions. `suppressed_emails`, used `email_unsubscribe_tokens` and the existing never-email rules determine announcement suppression. Preview, enqueue and delivery perform no Resend requests and require no Resend key. Database verification errors fail instead of being treated as exclusions. The recipient guard runs again after rendering, immediately before audit and enqueue; both the HTTP queue worker and admin queue processor independently repeat it before sending, even when a queued message already contains an unsubscribe token. A member who expires or becomes held after review is withheld. Verification failures are recorded as failed and remain retryable under the existing queue policy. Legacy announcements resolve their saved audience; an unknown audience fails for review.

Known external opt-outs must be reconciled into native suppression before this correction is published. Prepare complete read-only evidence from the existing connected Resend account and have the independent auditor verify the account and exact deny-only import. Import only opted-out addresses with `reason = 'unsubscribe'` and source provenance in metadata; use `ON CONFLICT (email) DO NOTHING` to preserve every existing native denial and its reason. Never import an external subscribed state as permission or clear a suppression. Keep contact evidence and import SQL outside the public repository. No schema migration or Resend credential setup is needed. Future Resend-only opt-outs are not automatically mirrored; this is a one-time reconciliation, not a recurring snapshot or runtime freshness gate. Separate Resend segment reconciliation remains unchanged.

Preview performs only reads. Send submission persists the reviewed snapshot, admin ID and omitted identities/reasons in the existing admin audit logs and suppressed log entries. Those details never enter email content or queue payloads. The review changes no membership, grants, holds, suppression records or provider contacts. A UI acknowledgement is not a substitute for the owner's separate approval of final content and recipients. Publish application changes through Lovable after independent review and suppression reconciliation. No emails were sent during implementation or testing.

Verification uses synthetic Supabase responses and mocked Lovable delivery, plus the existing PGlite membership regression suite. Tests exercise both actual worker entry points, no-key preview/enqueue, mixed cohorts, exact exclusions, stale audience changes, expiry/reversal/suppression races, used-token denials, native read/audit errors, legacy queues, admin access, filtered campaigns and preservation of branding and content isolation.
