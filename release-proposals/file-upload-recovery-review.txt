Authenticated upload completion and pending-file recovery

The default file_upload begin response opens an MCP Apps upload card. One Add file to job action sends bytes to the existing short-lived upload capability, then calls the existing authenticated file_upload finish operation. Final success requires a member-visible document/piece readback and the exact company/job/upload/file identity. Failures retain the same upload ID; retries check current ownership, scope, status and expiry first. Lost completion responses are read back without another document save. Closing the card does not lose the server-side pending row: project_documents list exposes the caller's pending uploads and a Resume upload action in a fresh conversation.

Managed release prerequisite
Lovable Cloud must review and apply file-upload-recovery.sql before deploying the revised application. The proposal has not been applied. Default begin preflights this read surface before creating an upload; source-document reads remain available if recovery cannot be loaded. No independent backend dashboard, connector, credentials or workstation migration is required or authorized.

Read surface and security impact
- New authenticated RPC mcp_file_upload_recovery returns at most 25 records and a caller-owned pagination cursor for the currently selected job.
- Every read calls the canonical active-membership gate and current mcp_job_scope. Only full/contract scopes qualify; submittal-piece rows additionally require full scope.
- created_by must equal auth.uid(). A company owner cannot enumerate another member's private pending uploads through this surface.
- Returned fields are upload ID, already-authorized company/job IDs, filename, purpose, MIME type, timestamps, completion status and whether bytes have arrived. Tokens, token hashes, storage paths, file contents and other actors' IDs are omitted.
- No table grants, RLS policy changes, entitlement changes or service-role completion path are added. SECURITY DEFINER is limited to this checked read; PUBLIC/anonymous execute is revoked. The function is intentionally volatile because the existing membership gate can refresh its cache.
- Recovery, chunk and finish through file_upload require the same upload creator and current job access. This tightens cross-member continuation: saved job documents retain their existing role visibility, while another member's pending transfer cannot be continued through this tool.
- Explicit company selection is checked independently of the conversational resolver: an accessible job in company A cannot replace a requested company B.
- The card's cross-origin PUT uses credentials omit. The CSRF exception matches only the existing 43-character upload-capability route; POST and other routes remain protected. CORS grants no credentials and permits only PUT/OPTIONS. Token validation, financial upload claims and expiration remain on the existing route; registration still uses authenticated MCP calls.
- The card locks host-message origin/source after initialization, restricts uploads to the existing app capability URL, renders names as text, and stores only non-secret identity references in widget state/model context.

Scope and limits
This covers file_upload contracts/specifications/submittal pieces. Financial original approval/linking remains a separate workflow. A standalone link still represents byte receipt; it gains visible recovery through normal job-file listings rather than unauthenticated automatic registration. Hosts without MCP Apps server-tool capability use the same pending/resume/finish tools through conversation; that host fallback needs live acceptance testing. Expired transfers remain blocked even when bytes exist; an explicit new upload is required. No historical uploads or customer records are repaired or deleted by this patch. Estimating changes remain availability-message correctness only.

Verification
Card-script tests dispatch finish only when emitted by the actual card, covering contract/specification/submittal completion, same-ID retry, lost PUT/completion response, closed-card/fresh-chat recovery, repeat success, company/job/actor denial, inactive membership, expiry and pagination. Local PostgreSQL tests use the real migrated role predicates and the proposed checked read. MCP SDK tests verify card discovery/resources and preserve source-reading responses. Production host rendering and managed SQL application remain release acceptance steps, not claims made by the local tests.
