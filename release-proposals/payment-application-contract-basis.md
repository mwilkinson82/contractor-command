# Payment-application contract basis

The application calculator requires a known numeric original-contract fact, but the published form cannot enter it. The payment-application page now offers an inline original amount and source-reference editor. It reviews the approved total against the saved SOV, asks once to confirm the fact save, then reloads the actual canonical application prerequisites. This creates no invoice, certificate, credit, receipt or allocation.

The source is explicitly member-provided. A typed reference is not independent document or approval verification. Original contract and approved change orders stay separate; no SOV amount is silently adopted as an approved contract. Existing change-order reconciliation and the canonical snapshot remain authoritative.

The unapplied SQL proposal adds one private helper behind the existing authenticated billing RPC, reusing its active-member/full-job checks, review tickets, operation outcomes and guarded fact writer. It changes no existing grants, roles, policies or signatures. The helper revokes PUBLIC/anon/authenticated execute. Apply only through the reviewed Lovable Cloud native migration runner; never run it directly against customer records.

Reviews bind exact amount, reference, actor, job, request ID and current source-version fingerprint. Saves lock the source facts, compare the reviewed context, consume one unexpired ticket, call the existing fact writer and validate the actual canonical snapshot in one transaction. Missing fact rows are acquired without overwriting a concurrent insertion; any stale context or failed prerequisite rolls back placeholder rows, audit and ticket consumption. Operation signatures include the contract-basis action family, and membership/job checks precede cached outcomes. Repeated and lost-response requests retain the same identity, rather than reapplying the update. A subsequent source change invalidates outstanding payment-application reviews.

The browser persists only the exact pending request under its actor/job key. Reload offers outcome checking or same-request retry. An unapplied request returns to review; an expired or stale review does not silently rebase. Editing or cancelling invalidates delayed review responses. Cached contract details are hidden on read failure. A saved contract basis is not described as refreshed if the follow-up reads fail.

Verification includes actual isolated SQL and the real React form starting with a missing contract amount, explicit confirmation, stale source, cancelled delayed review, newer inputs, interrupted save/reload and entry into the application editor. Browser transport is a synthetic fixture; it does not replace database authorization tests. Native independent-session concurrency, managed installation and authenticated live acceptance remain release checks. No owner proposal values or production records are saved by this repair preparation.
