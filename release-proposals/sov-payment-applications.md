# Saved SOV payment applications

This proposal adds versioned application records behind the existing authenticated billing RPC. Apply the SQL only through the reviewed Lovable Cloud migration lane. Application publication and managed migration installation are separate release steps.

Draft and ready applications do not issue billing. Submission atomically creates one linked `pay_application` billing record for the current requested amount. Certification adds a version to that same identity. Cumulative completed work is never inserted as a second invoice. Existing cash allocations and posted credits remain separate. If previous issued requests exceed actual certificates, reconcile them explicitly before issuing the next request; cash is never used as certification.

Every continuation freezes its canonical SOV fingerprint, exact scheduled values, period/cutoff, installed work, stored balance, explicit stored-to-installed transfer, retainage rates and approved cumulative releases. A stored transfer cannot exceed prior stock or installed work this period. The new eligible stored amount is current storage minus prior storage plus the transfer. Missing numeric inputs remain null. Rates, prior certificates and prior zeros require explicit input. The current SOV must tie to the recorded approved contract/change-order basis.

Read/review/save use current active-member and full-job checks. New tables have RLS enabled and no PUBLIC/anon/authenticated privileges. Internal helper functions have no PUBLIC/anon/authenticated execute privilege. No new authenticated RPC grant, policy, role, token or entitlement is introduced. The existing RPC is extended in place with a checked source patch, preserving its signature, owner, ACL and security/search-path settings. Legacy invoice mutation refuses application-managed identities. Existing receipt, credit, original-document and allocation paths retain their controls.

Reviews expire after fifteen minutes and bind the actor, job, exact payload and current SOV/evidence/calculation context. Saves recheck all sources under the existing job lock, consume one review atomically and retain the request ID/result for lost-response retries. Expected versions, unique numbers, issued-period overlap and exact predecessor certificates prevent stale or competing writes. Saved versions are immutable; a substantive revision requires a new exact review, expected version and reason, updates the same linked billing identity and cannot undercut allocated cash or posted credits. Unsupported negative applications require the separate reviewed credit/correction workflow, never silent replacement. Revisions of certificates referenced by later saved applications stop for lineage reconciliation.

The signed-in application route preserves the selected ID/version across sign-in and browser history. Missing/inaccessible versions show a targeted error. Its PDF is generated from the exact saved snapshot, with Athena branding and status; it is not an official proprietary form, signature or independent certification. Exact billing links connect evidence, history and originals. The separate `/payapp` route remains the monthly billing forecast; `field_pay_app` remains a daily progress preview and propagates missing aggregate inputs.

Before installation: independently review the exact SQL bytes, function-shape preflight and local database/security tests. Before application publication: verify the managed migration receipt and installed definitions/ACLs, then complete an authorized synthetic conversation → review → confirm → saved version → PDF acceptance. Do not create production progress or certificate facts to fill missing inputs.

Rollback is an application/tool rollback if needed. Do not drop application versions or linked financial evidence after real saves. Preserve records and reconcile any affected accounting facts through the normal reviewed correction workflow.
